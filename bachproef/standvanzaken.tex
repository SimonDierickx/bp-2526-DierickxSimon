\section{Requirements for emergency communication}%
\label{sec:sota-requirements}

Before anything can be evaluated, let's define emergency communication demands. When the primary infra fails (such as cellular or internet), the replacement provided should satisfy a list of requirements that is different from our everyday solutions.
The needs identified are usually the same, \textcite{ManojBaker2007} state that one of the primary challenges is responding to disasters itself. The tools responders and public use should be affordable, available and usable in daily life.
In a review of communication technologies for difficult terrain they test robustness, rapid deployability, cost and energy efficiency as well as quality criteria \autocite{ElKhaledMcheick2019}.
The five criteria listed below are the ones used throughout this thesis.

The first and maybe most important, requirement is \textbf{the independence from fixed infrastructure}. If a solution is found but it only works relying on the central tower or on a data centre the same failure as the outage applies. Which means the solution is unusable.
This is exactly what motivates us to find an autonomous solution \autocite{ManojBaker2007}. This is not just a theoretical thing, when a disaster hits, the fixed infrastructure usually goes down first. So what does this mean, the network everything is dependent on goes down when it's needed \autocite{ManojBaker2007}.
Therefore, a solution that still relies on that same infrastructure is not a solution, it just has the exact same weakness. Real independence means the solution has to be able to generate its own connectivity when being deployed.

Another requirement is \textbf{quick and easy deployability}. If there is a crisis, there is no time for licences, specialists or training.
The emergency solution should be set up and ready by ``general public'' in minutes using the right documentation and instructions.

The third requirement is \textbf{affordability at scale}. Only if there are enough participants the emergency solution is useful, which means if buying in to this network is impossible for most ``normal'' people, then the solution in itself is not useful at all.
This applies to subscription and per-message fees based solutions as well, especially for larger scale operations. The idea of being able to scale it is what makes the cost so important. One device costing \euro{}200.00 is expensive, but it is somewhat ok, if you need to buy 10 of those devices, that changes it completely.
If the entry price or recurring costs (subscriptions, extra fees, etc.) are too high, the network stays too small to be really useful. \textcite{ElKhaledMcheick2019} point this out as well when talking about cost and energy efficiency as an evaluation criteria for communication in difficult conditions.

Range and reliability are of course one of the main requirements. The solution must be able to cover a meaningful distance in order for it to be realistically deployable. 
Meaning that in a real-life scenario and terrain, messages should be delivered with an acceptable success rate, with ideally a possibility to extend its range if necessary.
Especially in situations where the duration and scope of the emergency is unknown or undetermined.

The last main requirement found is the \textbf{security and privacy} of said solutions. In some specific cases (wars, censorship, etc.) the communication could contain sensitive information which shouldn't be intercepted and might be targeted by attacks/snooping.
As discussed in section~\ref{sec:sota-security}, this is desirable, but it isn't always as straightforward as it seems.

These five requirements form the main evaluation criteria for this thesis. They will be used to compare different alternatives as a solution for the main research question.

\section{APRS (Automatic Packet Reporting System)}%
\label{sec:sota-aprs}

\gls{aprs} is a known protocol, it's used with amateur radio frequencies, enabling real-time communication of position and telemetric info on said shared frequencies \autocite{ManojBaker2007}.
It is however relevant to emergency contexts as it operates independently from the internet. \textcite{ManojBaker2007} demonstrate this in a real-world disaster (this happened in Cambodia). Both the response and mobile station operators relied on licensed amateur radios.

The licence is in fact the biggest barrier to rapid deployment, in a conflict scenario those licences could be revoked or the frequencies seized by the authorities. And in case of a natural disaster, there is most likely no time will be spent on giving out radio licences.
It also depends on specialized hardware, which makes it difficult to configure and place, especially in crisis conditions. If we compare this to the previously mentioned requirements, \gls{aprs} is infrastructure independent, but it fails for the easy and quick deploy.

\section{DMR (Digital Mobile Radio)}%
\label{sec:sota-dmr}

\gls{dmr}, just like \gls{aprs}, is a protocol based on radio, namely digital mobile radio standard as defined in \textcite{ETSI2023DMR} by the \gls{etsi}.
It is defined in three tiers:
\begin{itemize}
    \item Tier-I: licence-free, low-power, short-range
    \item Tier-II: licensed, \gls{tdma} equipment (voice and IP data), repeater-based communication 
    \item Tier-III: licensed, trunked, \gls{tdma} equipment (voice and IP data), repeater-based communication
\end{itemize}

\textcite{Nyawose2025DMR} confirm the improvements in efficiency, quality and security \gls{dmr} offers, this compared to analogue radio.

It is however not a suitable solution for emergency communication.
Tier-I is definitely not suitable because of the severe range limitations. Tier-II and III require licences, which is one of the main requirements and place it in the same position as \gls{aprs}.
The dependence on specialized hardware is once again limiting the deployment, especially because it's also dependent on repeaters, which may be failing due to the same outage as the primary infrastructure.
\gls{dmr} satisfies range and reliability, but it fails for licensing and deployability.

\section{Satellite messengers}%
\label{sec:sota-satellite}

Commercial satellite based messengers (e.g. Garmin inReach, Zoleo, Bivy Stick, SPOT, etc.) provide a genuinely off-grid solution, relying on satellite infrastructure instead of terrestrial infrastructure. 
The principal advantage they have over any other solution is the global coverage, which makes the range requirement completely irrelevant.

This technology, with all the advantages it has, isn't something that is easily accessible to everyone. The devices are really expensive and on top of the initial purchase amount a subscription fee adds up \autocite{GarminInReach2026, Zoleo2026}.
As seen on both the constructors' websites, a Garmin inReach Mini 2 costs \euro{}349.99 \autocite{GarminInReachMini22026} to buy, on top of this price the mandatory subscription of \euro{}9.99 up to \euro{}59.99 per month \autocite{GarminInReach2026} needs to be paid. Depending on the exact subscription chosen, per message fees can be added as well; they can be found on \textcite{GarminInReach2026}.
This is the case for Zoleo as well, the device start at \euro{}249.00 \autocite{ZoleoProducts2026}, with an additional subscription fee of \euro{}17.99 to \euro{}34.99 \autocite{Zoleo2026}. For Zoleo as well, depending on the exact subscription per-message fees can be added. 

This means it's impossible to scale, especially for general public associations like volunteer organisations or municipal safety services. Especially the recurring cost make it almost impossible to deploy at scale.
The satellite messengers satisfy the independence and range requirements, but horrendously fail on affordability at scale.

\section{LoRa}%
\label{sec:sota-lora}

Before diving into the whole Meshtastic architecture, it's important to understand the technology it is built on, \gls{lora}.
\gls{lora} is a physical-layer protocol, grouped under the \gls{lpwan} umbrella, that modulates radio signals in the \emph{``sub-GHz''} \gls{ism} band; these are free to use and unlicensed frequencies. To modulate they use \gls{css}, which is developed and sold by Semtech \autocite{Raza2017LPWAN}.
How it works is, instead of sending on a fixed narrowband, \gls{lora} spreads the input signal over a wider channel using chirps. A chirp is a signal of which the frequency sweeps up (or down) across the whole bandwidth.
This results in noise-like properties on the signal, which makes it more resistant to interferences, and make distant nodes able to decode the signal even if the signal is heavily polluted by noise.
This is exactly why \gls{lora} is good at long distances at low transmit power \autocite{Raza2017LPWAN}.

To achieve this, the \gls{sf} parameter is configured. It ranges from 6 to 12 and controls the balance between range and data rate.
A higher \gls{sf} means longer chirps which means higher range, but lower data rate. The \gls{sf} combined with the bandwidth and coding rate determines the sensitivity and the throughput \autocite{Raza2017LPWAN}.
This is important to understand, because depending on the use case it might be better to sacrifice the range for the speed at which the message is sent, and vice versa. In our use case, range matters more. This is the reason why we set \texttt{LONG\_FAST} as a setting preset (see chapter~\ref{ch:poc}).
The hardware used in this thesis (Heltec V4 with Semtech SX1262 transceiver) has a maximum sensitivity of $-148$ dBm, which is achieved with a \gls{sf} of 12.
According to \textcite{Janssen2020LoRaRange}, sub-GHz \gls{lora} can do between 10 and 15\,km in rural/open areas, in urban areas this drops to a few km according to the obstruction. This means anything over 10/15\,km could be seen as a strong result.
\textcite{Ma2024ForestAttenuation} also shows us that vegetation and trees significantly reduce the radio signals. This can cause severe signal loss.
The range is also determined by the antenna. A higher antenna position (less obstructions = less path loss) and a more sensitive receiver (better antenna) means a higher range. This also explains why a similar location with a few trees in between can have a connection or not as clearly seen in chapter~\ref{ch:poc}.

\gls{lora} comes with some limitations as well, in Europe it only allows operation on the 868\,MHz band. It is also subject to duty-cycle and power limitations. These are defined by \gls{etsi}, and in Belgium by \gls{bipt}. 
These limitations directed us in the right direction for the used config in the \gls{poc}; this can be found in chapter~\ref{ch:methodologie}.

\gls{lora} in itself isn't how the nodes form a network; it is just a modulation protocol. The most known layer built on top of \gls{lora} is LoRaWAN.
It organises end-devices in a star-topology network around fixed gateways. This dependency on gateways introduces the exact same main infrastructure dependence problem as the other solutions. Here is where Meshtastic shows a different approach.

The usage of \gls{lora} for off-grid emergency communication has been explored, for example in \textcite{Hochst2020LoRa}, they evaluate \gls{lora}-based communication for crisis situations. This showed a range of 4.6 to 6.5\,km, with a base node placed on a high building (depending on the used antenna and frequency).
This provides a useful comparison to the measurements in chapter~\ref{ch:poc}.

\section{Meshtastic}%
\label{sec:sota-meshtastic}

Now \gls{lora} has been explained, the base of Meshtastic is clear. Meshtastic itself is an open-source firmware that turns simple microcontrollers (mostly ESP32) into nodes of a decentralized mesh network \autocite{MeshtasticDocs}.
It has attracted academic attention over the last few years as an off-grid emergency alternative: \textcite{SepulvedaMeshtastic2026} analyses the resilience of Meshtastic networks and its modem presets in long-range propagation scenarios, confirming that each node can act as a router and a client. Unlike LoRaWAN, it doesn't depend on gateways, each node can both create, forward and receive traffic.
The network is also self-healing. This means that the route automatically adjusts whenever a node appears or disappears. This is really useful in emergency cases, where a node can suddenly be unavailable or be added.

How do messages actually travel through the mesh: Meshtastic uses \gls{csma}/CA to avoid any collisions on the shared frequency. Each node forwards messages that are not meant only for itself using managed flooding (rebroadcasting). This way it reaches nodes further away.
This is done until the message reaches the destination or the hop limit is reached \autocite{Durand2025MeshLoRa}.
\textcite{Durand2025MeshLoRa} evaluate a \gls{lora}-based mesh network and shows that multi-hop forwarding improves the \gls{pdr} for nodes far away from the destination. This is exactly the supposed effect of a relay node.

Each node is independent: it requires no SIM card, no internet connection and no licence.

Different roles can be attributed to the nodes, a \texttt{CLIENT} node is an endpoint operated by a user; a \texttt{ROUTER} node is optimized to only relay traffic and a \texttt{CLIENT\_BASE} node combines both, allowing the node to forward traffic while also being able to connect to a user as an end-device.
Messages go from one node to another, with a maximum hop limit you can set up in the app.

Meshtastic puts nodes into different channels, each channel is named, encrypted and defined by a \gls{psk} \autocite{MeshtasticChannels}.
A device wanting to participate in said channel, must have the same channel name and \gls{psk} configured. Eight different channels can be configured on a single node simultaneously, one primary and seven secondary channels, each with its own key \autocite{MeshtasticChannels}.
Figure~\ref{fig:meshtastic-channel} shows the channel configuration in the Meshtastic client.

The above mentioned properties are the ones that make Meshtastic a potential candidate for our problem. It's inexpensive, licence-free, quick to deploy, all of this falls into the deployability and affordability requirements that were defined earlier. The questions left to answer to check if Meshtastic is in fact a suitable candidate are: range, reliability and security in emergency cases.

\section{Meshtastic security model}%
\label{sec:sota-security}

One of the sub-questions was the security of Meshtastic in case of traffic interception. That's why Meshtastic's encryption model deserves a dedicated analysis.

Meshtastic encrypts the payload of each of its channels using \gls{aes} in \gls{ctr} mode, with a distinct key per channel \autocite{MeshtasticEncryption}. 
The \gls{aes} encryption itself is considered secure, In \textcite{NIST2023AES} it is the approved standard for protecting sensitive information. It has been analysed for more than twenty years and is still considered secure to use \autocite{Bogdanov2011AES}.
The known limitations come from the implementation, not the encryption itself, as specified down below.

One of the crucial decisions of Meshtastic is to only encrypt the payload, which means the packet header (containing send node number, packet identifier and hop limit) is not encrypted and always transmitted in cleartext \autocite{MeshtasticEncryption}.
This design is intentional, this makes routing possible, the route is chosen on the basis of the cleartext header, so that any node can forward it. That makes each node a relay, even when it can't decrypt the payload and read the message.
This means confidentiality of the message content and participation in routing are independent: a third-party node can carry traffic without reading it.

The most important limitation concerns the default channel, which contains a default publicly known key, encoded as \texttt{AQ==} in Base64 \autocite{MeshtasticChannels}.
This means any device worldwide could decrypt traffic on this default channel, so for that case no real security or confidentiality is available until a private key is configured.
This requires replacing the default key with a random generated 256-bit \gls{psk}, after which only the devices who possess the key can read the content \autocite{MeshtasticEncryption}.

Even with a strong private key set up, limitations remain. \textcite{MeshtasticEncryptionLimitations} proves this, \gls{aes}-\gls{ctr} provides confidentiality for Meshtastic, but no authentication. This means anyone who can obtain/know the \gls{psk} can send messages impersonating another user.
Second of all, the cleartext header which is handy for routing exposes data to third parties, anyone being able to observe the packets can see the node identifiers and timing, even though the content stays unreadable.
Some recent firmware updates to Meshtastic (version 2.5 and later) add public-key cryptography but only to direct messages. These provide authentication for one-to-one communication. For group channels however, the shared-key model stays in place and stays risky.

The security aspect of Meshtastic has also been getting some academic attention. \textcite{Messina2024Meshtastic} study the Meshtastic protocol, more specifically in an \gls{iot} security context. They confirm both findings. The strengths: dynamic and adaptable mesh with per-channel encryption but also the weakness being: the dependence on how the channel keys are managed.

Table~\ref{tab:sota-comparison} makes the trade-offs from Meshtastic explicit.
On paper, Meshtastic wins on the cost, licence-free operation and ease of deployment requirements. However, it pays for this with very low throughput, text and telemetry only (no voice), and no guaranteed delivery, since \gls{lora} traffic is best-effort with no acknowledgement mechanism by design.
Its mesh nature also means reliable coverage depends on sufficient node density (if no nodes, no communication), whereas \gls{dmr} and satellite systems do not.
Based on documentation alone, Meshtastic looks like a strong fit, especially for a low-cost, infrastructure-independent, text-based scenario. Whether it actually delivers reliable range and coverage is exactly what the \gls{poc} in chapter~\ref{ch:poc} is made for.
